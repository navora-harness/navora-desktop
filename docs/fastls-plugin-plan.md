# Fastls 插件与 fastls-curl 集成规划

日期：2026-11-01。状态：等待用户开发并交付 `fastls-curl`，再实施插件集成。通用安装机制见 [插件跨平台安装规划](./plugin-platform-installation-plan.md)。

## 1. 已确定的边界

`fastls-curl` 由用户开发。Navora 后续负责二进制的分平台打包、安装、受控调用和 Agent 工具适配，不另行实现 Fastls 网络内核或维护专用 Go worker。

调用关系为 `Navora 插件 → 宿主 runtime 服务 → fastls-curl 二进制`。插件 ID 暂定 `fastls`，工具使用 `fastls_` 前缀；具体名称和版本在接入时冻结。

此前 Node SDK、随包 Node、Koffi 和 worker JavaScript 的集成路线已被替代。通用平台安装、摘要校验、失败回滚、权限和子进程清理规划继续保留。

## 2. 等待交付的对接信息

以下是后续集成清单，不表示 fastls-curl 已实现这些接口，也不要求其现在采用某种固定协议。

- **发布物**：版本号、下载位置、各 OS/架构文件、SHA-256、许可及必要配套文件；说明单文件还是依赖动态库、证书或 profile 数据。
- **运行条件**：最低 Windows/macOS/Linux 版本、Linux libc 要求、执行文件架构；如提供静态链接 Linux 产物，明确其实际依赖和验证范围。
- **调用方式**：一次性命令行还是持久进程；请求参数、请求体和凭据的输入方式；是否支持 stdin 或结构化配置输入。
- **机器可读输出**：状态码、响应头、最终 URL、协议、正文及编码、错误；stdout、stderr 和退出码各自的约定。HTTP 4xx/5xx 与进程/传输失败需能区分。
- **资源控制**：超时、取消/终止、最大响应和解压大小；是否支持流式输出、重定向开关和逐跳控制。
- **能力发现**：版本及能力查询方式；profile、代理、Cookie、会话、HTTP/3 等以实际公开接口为准。

不假定名称含 curl 就完全兼容 curl 参数、退出码、配置文件或 Cookie jar 格式。参数映射以 fastls-curl 文档和固定版本实测为准。

## 3. 调用模式适配

优先按 fastls-curl 原生接口接入，不为插件集成强加后台服务。

如果是一次性 CLI，宿主每次调用启动一个进程，经支持的输入渠道传请求，持续消费 stdout/stderr 并限制缓冲；完成后按退出码和机器可读结果解析。取消时终止对应进程及其子进程。复用连接或长期会话不作为前置承诺。

如果提供持久模式，再适配请求 ID、并发、取消、会话、进程退出及崩溃恢复；必须有明确的响应关联和协议版本。不自动假设存在 JSON-RPC、HTTP 端口或 stdio 帧。

敏感内容优先通过 stdin 或私有受控输入传递，避免放进命令行。若接口必须使用临时文件，文件仅对当前用户可读，调用结束清理；具体方式待契约确认。宿主使用参数数组和 shell:false，Windows 隐藏窗口，不拼接 shell 命令。

## 4. 插件包与平台选择

每个平台 ZIP 包含 `plugin.json`、纯 JS 桥接入口 `main.cjs`、README、运行文件清单、许可及 `bin/fastls-curl[.exe]`，并按实际产物携带必要配套文件。用户机器无需安装 Node、npm、Go 或编译器来运行该二进制。

运行时使用通用 `executable-sidecar` 声明；记录二进制版本、调用方式和协议标识。SDK 复制构建阶段已经校验的目标产物，不在用户安装阶段编译或临时寻找系统同名命令。

同一插件版本可发布多个 artifact，由宿主按真实执行架构、系统及声明的 libc 条件选择。Windows amd64 映射 win32-x64 等命名转换显式配置；不能通过修改文件名把一个架构的二进制标为另一个架构。

候选验证顺序为 Windows x64，然后按 fastls-curl 实际发布目标扩展。Windows arm64、musl 或静态 Linux 目标仅在交付并验证后纳入；不沿用 npm 包的平台限制，也不预先承诺支持。

## 5. Agent 工具范围

第一批计划 `fastls_status` 和 `fastls_request`。status 查询包版本、平台及进程可用性；request 适配 URL、method、headers、正文、代理、超时和结果。实际参数集合以二进制能力为上限，不支持的字段明确拒绝。

结果统一区分工具执行是否成功与 HTTP 是否为 200–299，保留多值响应头、正文编码、最终 URL 和截断标记。HTTP 错误响应不伪装成安装或进程故障；诊断不泄漏凭据。

profile 列表仅在存在可靠查询/固定版本数据时开放。原规划的 session_create/list/close、Cookie CRUD、SSE/WebSocket 和 HTTP/3 暂列候选，等待 fastls-curl 实际能力再决定，不为未提供的功能编造实现。浏览器 Cookie、代理和 UA 不自动共享。

## 6. 权限与资源控制

沿用新增 `network.request` 的规划，纳入默认预设、配置迁移、SDK 和界面。status 使用 compute.local；未来 Cookie 或文件操作按实际工具分别声明读写权限。插件不能用 shell.exec 替代受控二进制调用。

URL 仅允许 HTTP/HTTPS，使用严格网络 URL 匹配规则。每次请求应用当前宿主白名单；若二进制无法对自动跳转逐跳执行相同策略，首期禁用自动重定向，不能仅校验起始 URL 后允许任意跳转。

请求取消、停止 Agent、删除 chat、停用/卸载/升级插件和应用退出均回收相关进程；崩溃后不自动重放已发出的请求。持久模式才涉及会话过期及 idle 回收，具体参数待接入实测。

初始预算候选为输入正文 1 MiB、解压后响应 8 MiB、返回模型正文 64 KiB、单次默认超时 30 秒。接入时确认二进制能否在读取/解压阶段施加硬上限；只截断最终工具文本不能声称已限制二进制内存。无法满足必要预算的能力先不开放。

## 7. 实施顺序与验收

1. 通用平台安装机制可独立推进，使用测试可执行文件验证安装、调用、取消、更新和回滚，不依赖 fastls-curl 开发进度。
2. 用户交付 fastls-curl 后，先冻结一个版本、调用说明、平台产物和摘要，完成无插件的最小调用验证。
3. 实现 SDK 产物收集、宿主适配器和 status/request 工具，在无系统开发工具的 Windows x64 环境完成安装与请求闭环。
4. 验证 HTTP 错误、代理、超时、取消、重定向限制、大/压缩响应、脱敏、中文/空格路径、无控制台闪窗、进程回收及升级失败恢复。
5. 按实际能力逐步接会话、Cookie 和其他协议；按实际发布目标分别完成安装、调用、分发验证后上架。

交付前核对二进制及配套文件完整性、版本/协议一致性、目标平台运行条件、macOS 签名/公证、Linux 执行权限和系统依赖。安装自检优先使用实际提供的不联网版本/能力查询，不假定存在 health 子命令。

当前不创建虚构的下载地址、命令参数或可运行插件骨架。后续集成的外部依赖是用户提供的 fastls-curl，通用安装机制无需等待其接口全部确定才开始。
