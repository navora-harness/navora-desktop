## 为什么持续走无效路线

### 直链优先指引缺少前提

`shared/agent-prompt.ts` 和 `shared/agent-tools.ts` 引导“已有完整下载链接时用 file_download”，容易把配置文件中的静态 URL 视为可直接使用的下载链接。但本次实际可用的请求是点击后带签名的 URL。

`electron/modules/file-download.ts` 对 403 的提示继续要求绑定 Session/Window、携带 Referer，没有区分这些条件是否已经提供。聊天确实沿着该提示再次请求。同一个缺少签名的资源因此被不同工具和不同请求头反复尝试。

### 宿主把普通布局误报为遮挡

`electron/modules/page-blocker-observer.ts` 将 `main/form/body` 纳入候选；`fixed/absolute` 且面积超过视口 12% 的元素可被认作模态容器，容器内普通控件又可构成所谓 challengeControl。分类器据此确认 `other_overlay`。

隔离复现：普通全屏 absolute body 内只有一个正常按钮，没有 dialog 或验证码，仍得到 `confirmed / other_overlay / yes`；仅把同一个 body 改为 static 即得到 `not_observed / no`。这证明代码存在误报路径。结合现场截图和较早任务在同类报告下仍能点击下载，现场遮挡提示不可靠；未采到 QQ 原始 computed style，不把隔离样式冒充 QQ 的已记录样式。

### 引用失效后的恢复方式不正确

`electron/modules/browser-native-refs.ts` 每次原生快照替换引用集合。生成新快照后，旧引用被拒绝是正确保护。模型应重新按文字定位并点击当前引用；本次却先使用旧引用，再加上不符合目标实际角色的 button 过滤条件，进一步远离可用路径。

### 进展策略按工具参数计数，缺少资源层面的归并

`shared/agent-progress-policy.ts` 通常按工具名、完整参数和错误码计算重复失败。换 Referer、会话或工具会产生新指纹；成功的非观察调用还会重置部分失败序列。下载目标和缺失前提没有跨工具归并。

此外，shell 工具的外层 `ok:true` 表示执行工具成功，不保证 HTTP 或业务成功。现场有退出码 1 仍显示工具完成的调用，也有 curl 收到 HTTP 403 仍正常退出的调用。它们不应被当作下载取得进展。仅查询文件、看到旧版本文件、或切换下载渠道也不足以证明原目标已完成。

## 建议的修复顺序

1. 下载指引区分静态 URL 与页面授权后产生的 URL；已有官方可操作按钮时优先完成官方流程，并检查宿主下载事件。
2. 403 提示根据已提供的 Session/Window/Referer 改变建议；相同前提下失败后转为页面流程，避免机械重复同一提示。
3. 遮挡判断要求独立遮罩、实际命中拦截或明确模态语义等证据，避免用普通 body/main 布局及按钮证明页面被挡；真实验证和人工交还仍须保留。
4. 旧引用失效后重新观察并使用新引用；不要把可点击目标限定成 role=button。
5. 进展策略按下载资源和缺失前提跨工具归并，解析 HTTP/进程结果；同路线无新增证据时停止重试，重新选择前提不同的路径。不能仅靠缩小调用次数上限。
6. 完成前核对期望版本、实际文件和下载状态。旧版本的下载不能自动替代最新官方下载目标。

本次按用户要求完成分析；上述 QQ 执行策略修复尚未并入产品代码，避免把诊断建议写成已实现功能。
