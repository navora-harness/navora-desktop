## 3. F02：原生目标文本输入适配错误——直接原因

### 已确认的契约冲突

[原生目标输入分支](../electron/modules/browser-tools.ts:3067)先组装 6 个选择／清空事件，再把完整文本放入单个 `{type:'char', text}`；到全部派发后才集中检查失败。

`.7` 对应源码提交为 `782f7d28c0e92aa670287a1592f51bb4868f9518`，本地对应文件已核对：

- Chromium `third_party/blink/public/common/input/web_keyboard_event.h:21` 定义 `kTextLengthCap = 4`。
- Electron `shell/browser/api/electron_api_web_contents.cc:5143` 的 `SetDispatchKeyboardEventText` 转成 UTF-16，要求 `text16.size() < 4`，预留结尾空位，**单次最多 3 个 UTF-16 单元**。
- 同文件 `:6403` 对超限文本返回本次实际出现的 `Invalid 'text' parameter`。

八字文本占 8 个 UTF-16 单元，精确命中限制；长 ASCII 文本同样可能失败，不能归结为“网站不支持中文”。字符派发失败后应用已提前返回，Enter 没有执行。此项首先是应用把键盘字符事件当成任意长度文本输入使用，**现有 `.7` 下即可修正常用输入，不必整体等待新内核**。

### 修复要求

1. **先规划，再改变页面。** 在任何选择／清空前验证文本类型、长度边界、Unicode 有效性、目标编辑能力及当前文档／控制权。拒绝只读、禁用、非编辑和已失效目标，避免失败后先把原文清掉。
2. 原生目标输入按真实 API 契约生成 Unicode 安全事件序列，单事件不超过 3 个 UTF-16 单元，绝不拆代理对；可按码点逐个发送。长组合序列、换行及复杂编辑行为单独验证，不能把正确分片等同于完整 IME／富文本能力。
3. 每一步检查回执，首个失败立即停止后续编辑与提交，只完成必要的按键释放和安全清理；不能把一串事件全部发送后再发现开头已经失败。
4. 明确替换／追加／空文本／提交语义；macOS 使用正确的选择修饰键。成功输入并按要求核实后才进入 Enter 提交，提交结果与导航／页面业务结果分别报告。
5. 失败回执记录失败阶段、已派发步骤、是否尝试清空、已确认文本量及是否提交；无法确认的结果标为未知。不要在通用日志记录正文或凭据，也不要盲目重放整段输入、自动恢复旧值或换用脚本赋值掩盖失败。
6. 保留 target／document／epoch、取消、来源和输入保护校验。部分派发后必须重新观察当前值／焦点，再决定有界恢复；用户手动接管后不得继续输入。

### 同路径发现的风险

- `.7` 的 `lib/browser/api/web-contents.ts:1322` 在原生文本参数校验前准备目标并滚动、聚焦。无效文本仍可能产生聚焦副作用，因此应用的纯参数检查应前置。
- `shell/renderer/electron_api_service_impl.cc:1207` 检查文档、连接、启用、可见及聚焦，但未统一保证目标可编辑／非只读；应用需要补齐编辑能力判断，后端仍需在实际派发时验证目标有效性。
- 当前[3072 行之后的清空序列](../electron/modules/browser-tools.ts:3072)只在末尾汇总失败，存在先前失败后仍继续派发的风险。

## 4. F03：查询型效率提醒——提前结束的促因与恢复缺口

[运行循环](../electron/modules/agent-runtime.ts:1020)在工具返回后调用[通用效率函数](../electron/modules/agent-runtime.ts:2671)，没有区分查询、规划和操作任务：

- 4 次时提示尽快作答；6 次时以 system 消息要求“立即作答，禁止继续 navigate/click/find/back/file_list”；8 次及以后偶数次要求不再调用任何工具。
- 独立的真正轮数预算仍由[配置及轮数检查](../electron/modules/agent-runtime.ts:758)管理，默认 24 轮。不能把提醒中的“强制”文案当作真实后端限额。
- 首项在失败后做了必要复查，恰好累计 6 次；结束答复说明了停止。这与无差别提醒机制高度一致，是提前收尾的重要促因。历史没有保存实际注入消息的完整审计，不能认定模型停止的唯一原因；后续应记录提醒原因与策略版本。
- 现有[不完整回复检测](../shared/incomplete-reply.ts:46)主要覆盖空文本、长度截断及简短计划话术；较长、形式完整的失败总结可以直接进入[回复结束](../electron/modules/agent-runtime.ts:1286)。回复结束不等于用户操作目标完成。

修复要求：

1. 简单查询用证据充分度、重复访问和无进展判断是否应停止；明确的操作任务按用户目标、实际进度和剩余预算推进，不以总工具次数 4／6／8 禁止合法后续动作。
2. 使用任务意图和运行阶段管理策略；“自动化／计划”声明接入后可提供显式信息，但本修复不能等待声明功能完成。意图判断不能授予额外权限，也不能由网页文本改变。
3. 保留轮数预算、超时、取消、权限和有界失败恢复；任务级时间／成本预算另行明确策略，不暗示当前已有对应硬限额。连续相同失败、页面无进展、输入效果未知时停止并解释；不能为避免提前结束而无限尝试。
4. 可恢复错误先完成必要观察，在既有授权内继续可验证步骤；部分输入或提交结果未知时先核实，禁止自动重放有副作用的操作。恢复不应机械要求用户再发“继续”。
5. 最终答复区分参数错误、页面拒绝、用户取消、预算耗尽、宿主策略停止和模型主动结束，保存实际 stopReason／policyReason，不能把文本提醒转述成已证实的运行时限额。
6. 审查运行循环中其它“信息不足也立即答复”的固定话术，特别是[宿主代读恢复](../electron/modules/agent-runtime.ts:1177)的“关于新手机／页面内容”模板；统一按实际任务阶段处理。该分支是额外发现的风险，尚无证据证明本轮触发。

## 5. O01：观察结果与诊断信息优化

- 本轮 `agent_snapshot` 携带 `agentQuery`，但[快照分支](../electron/modules/browser-tools.ts:3212)只把过滤传给 `agent_find`。工具文案和参数校验应清楚区分两者；不支持的组合给明确提示，避免静默忽略后返回整页。
- 原生大快照包含不可见节点和样式文本，耗费模型上下文、掩埋可交互目标；提供有界、紧凑的模型结果，优先可见可操作节点，保留 ref、target、完整性、截断原因与按需扩大观察入口。
- [模型结果压缩](../shared/page-digest.ts:159)尚未针对原生 `elements` 结构处理；通用递归裁剪可能造成外层已截断、内层仍声称完整。明确模型层裁剪及原始覆盖范围，保留完整目标与 frame 信息，不能把未返回的节点当作不存在。
- 模型裁剪与原始工具回执分开；敏感值继续脱敏，不把 HTML／样式／网页文字提升为指令。
- 增加 run／page／request 关联、编辑阶段与原生错误码、派发／效果确认、策略停止原因。页面加载的 `partial` 与动作部分执行分别表达，避免误读。诊断记录足以判断卡在哪一步，同时避免完整输入正文、账号、Cookie 等持久化。

以上为同路径优化，尚非本轮字符派发失败的直接原因。

## 7. 验收与实施顺序

1. 先完成 F02 输入契约与逐步失败处理，再完成 F03 任务感知的效率策略；两者分别验证，也做连贯集成验证，避免修好输入后仍在第六次提醒处提前结束。
2. 新增真实 `.7` 的隔离本地测试页，使用 `agent_snapshot／agent_find` 产生的原生 ref，覆盖 1／3／4／8 UTF-16 单元、长中文、ASCII、emoji／代理对、组合字符、多行、替换／追加／空文本及 Enter 提交。
3. 检查 input／textarea／contenteditable、只读／禁用／非编辑目标、iframe／shadow／隐藏页、焦点变化、文档刷新和手动接管；拒绝路径不得先清空原值，部分失败不能继续提交。
4. 注入首／中间／末步骤失败、延迟确认与取消，确认按键清理、控制权、已提交输入等待与回执一致；禁止超时假报成功或释放仍在执行的输入保护。
5. 连贯场景应完成“打开 → 定位 → 输入 → 提交 → 验证 → 滚动／点击 → 返回”，使用确实需要多步操作的夹具验证跨过 6／8 次仍按目标推进，不为凑次数添加无意义调用。另测简单查询能及时收束、无进展有界停止、真实预算耗尽与用户取消。
6. 当前 [browser smoke](../scripts/browser-smoke-entry.ts) 的主要输入覆盖使用旧 snapshot ref／`insertText`，原生 ref 在 [pointer smoke](../scripts/pointer-smoke-entry.ts)主要覆盖 hover／click。必须补上实际失败分支，不能用另一条输入路径通过来宣称修复。
