## 1. 产品语义

在“附加”中新增“声明”分组，用可选择的任务意图表达用户希望本条消息如何处理。声明是本条消息的结构化要求，与文件／网页资料引用、打开创建器、长期回答方式及会话权限分别管理。

首批提供两个声明：

- **自动化**：按目标使用合适的工具完成任务。按需采用直接导航、网页读取、Session/API 请求、文件或插件工具；必要时才进行可信点击、输入、滚动或拖动。不强制每个步骤都操作鼠标，也不要求每次回答都调用工具。
- **计划**：本条以形成方案、步骤和验收标准为目标，先不实施方案中的改动。可在已有授权内做必要的只读核对、检索，并生成用户要求的计划产物；不自动进入执行阶段。

两者可以组合：**自动化 + 计划**表示规划自动化任务，必要时做只读核对，本条仍停留在计划阶段。声明“自动化”不创建定时／循环任务，不切换浏览器人工接管状态，不改变公共或专用会话规则。

后续可扩展“调研”（收集资料、对照来源与证据）、“验证”（按已有目标检查并报告结果）。先保留稳定的扩展注册结构，未接入完整行为前不放可点击占位项，也不把“验证”解释成授权任意安装、修改或执行生产操作。首批只出现上述两个已接入声明。

## 2. 附加菜单与编辑区

附加菜单沿用户确认的 HTML 悬浮实现，位置继续在输入框上方、外缘左对齐，与原生菜单互斥；本项不改用 NativePanel。按钮和 `/` 共用命令定义。

- 菜单依次为“添加”“声明”“工具”，各组保留原有用途；声明放在文件／网页／会话之后、创建器之前，减少误把声明理解成浏览器资源的可能。
- “自动化”的短说明为“按需使用工具完成任务”；“计划”为“先制定方案，本条不实施”。长解释放在详情或提示中，不为每项增加多段帮助文字。
- 声明可以多选，右侧用勾选表示当前是否附加；它们不显示表示进入详情的箭头。来源项、创建器仍按各自既有流程执行。
- 搜索覆盖名称、说明及 automation／plan 等别名；中文、英文和斜杠入口选择相同声明 ID，搜索不会创建新的自定义指令。
- 选择后关闭浮层、恢复编辑焦点，编辑区正文上方按需出现可移除的小标签，例如“自动化 ×”“计划 ×”；仅有已选声明时才占用该行，不新增常驻工具栏。
- 标签作用于整条消息，不随文字光标所在段落改变；资料仍可以插在句中，不把声明做成伪文件引用或可编辑摘录。
- 再次选择同一项可取消，重复操作不产生两个标签；点标签主体可看简短含义，移除按钮有独立可访问名称。变更加入编辑器统一撤销／重做。
- 空间不足时标签换行，附加候选区内部滚动，滚动槽在条目外，搜索和底部提示保持可达。中文输入法确认、Esc、Enter、Tab、上下键及焦点恢复沿已有规则，不冒泡发送。

列表现有 `aria-selected` 表示键盘高亮，不能直接拿它表示多选结果。实施时需区分高亮项与已附加状态，以一致的 option 多选或 checkbox 语义向辅助技术表达，避免视觉已勾选但读屏只报焦点。

## 3. 本条作用范围与既有回答方式

声明默认只作用于当前草稿及其发送快照。成功提交后新草稿不继承；切换聊天、重启、失败恢复和队列编辑保留各自声明，不跨对话串入。用户历史消息显示短标签，可展开查看当时的语义；不把声明翻译成一大段常驻正文。

已有“自动／快速问答／执行任务”继续作为会话默认回答方式；声明不改写该配置。选了“自动化”时，本条可以进入工具可用的任务路径，并清楚显示“本条：自动化”；即使默认是快速问答，也不需要偷偷修改整个会话。单独选择“计划”时，本条采用计划阶段，按需提供获准的只读工具。模型选择与会话权限保持既有含义。

有效行为取会话默认、这条声明和任务正文共同解析；“计划”约束本条阶段，正文描述的实施目标可作为计划对象。正文与声明存在明确且无法消解的执行阶段矛盾时，澄清该矛盾，不能静默实施；不按“实现”等单个关键词强制拦截发送。后续用户明确要求开始执行时按已有授权继续，不额外要求固定确认词或按钮。

仅有声明、没有任务正文或有效资料时发送仍禁用，并提示输入任务。声明不凭空组成任务。没有勾选时，正文仍然可以正常表达自动化或计划要求，不能把菜单变成唯一入口。

## 4. 自动化与虚拟光标

“自动化”描述如何完成目标，不规定必须模拟人工路径。选择方法应考虑正确性、网站行为、效率、权限和可用能力。例如搜索任务可以直接导航搜索 URL、读取排序结果；需要登录、只能通过界面触发、页面流程必须交互或用户明确指定操作步骤时，再使用真实点击／输入。

- 直接导航、读取或 API 请求时，通过任务／工具状态说明正在做什么；不为了显示忙碌伪造鼠标移动。
- 实际鼠标输入发生时，光标跟随原生已派发事件和真实坐标转换；启用但尚无有效位置时保持图形隐藏，输入保护继续按租约生效。
- 纯导航／读取任务没有移动轨迹是正常行为。真正发生指针输入却不可见、初始零点残留、窗口恢复后错位属于独立呈现缺陷，仍按光标规划修复。
- “自动化”不要求每个步骤都打开或聚焦网页窗口，也不绕过现有前后台策略。需要后台执行时沿原有可信输入和宿主规则处理。

因此最新 GitHub 对话未移动鼠标，本身不作为 Agent 必须改用点击流程的缺陷；需要修的是初始光标错误显示和任务状态表达。用户明确要求逐步页面交互时，仍应按该具体要求执行。

## 5. 运行边界与消息队列

声明使用已注册、版本化的用户级语义，由主进程校验；不是把任意字符串拼入高优先级系统提示。文件、网页或引用中提到“自动化／计划”不会自动切换声明。

- 自动化启用可用工具，不提升权限，也不恢复已撤销授权；公共默认会话、专用隔离、敏感操作与现有权限门闸继续生效。
- 计划阶段必须同时约束工具派发和运行策略，不能只靠提示词“不要修改”。允许必要的读取／检索，限制实施性文件改动、网站提交、安装、清数据及其他产生任务效果的动作。
- 工具按实际操作与参数判断，不仅按名称或 GET／POST 分类；通用脚本、shell、浏览器 evaluate、插件等不能仅自报“只读”就放行。无法证明只读的动作在计划阶段返回限制说明。
- 用户要求保存计划文档时可在约定输出路径写入计划产物；该例外按用途和路径约束，不因为文件后缀为 `.md` 就放行任意修改。
- 子任务继承本轮阶段和约束，不能通过子 Agent、插件或通用工具绕过计划范围。能力未知的工具在该阶段保持限制，影响计划完整性时如实说明。
- 已开始的运行使用冻结的声明。首批运行中带声明的新消息采用入队处理，不能靠插入一条消息追溯改变已派发动作；需要改变当前任务阶段时沿现有停止／暂停与新任务路径处理。
- 队列在入队时冻结正文、资料、声明与非秘密模型配置；执行前复核当时有效权限。改队列中的声明需要更新该项修订，不影响正在运行任务。

“计划”限制是用户主动选择的阶段含义，不新增全局审批步骤，也不把普通自动化拆成每一步都需确认。

## 6. 数据与当前源码的接入点

现有 `ComposerAttachmentMenu.vue` 只区分来源选择和创建器，没有声明命令。`ComposerDocument` 当前为 schema 1/2，`compileComposerDocument()` 只编译正文、引用和来源；`ComposerSubmitInput` 也没有本条声明字段。运行时 `needsAgentTools()` 主要读取会话／模型快照的执行方式；新增 UI 标签而不改这些链路不会产生真实效果。

建议为文档增加版本化的任务声明元数据，采用新 schema 读取旧 1/2 文档，声明缺省为空。它属于草稿本身，不另建一份只存在组件状态的附件数组，也不扩成长期会话权限配置。

实施需要共同覆盖：

1. 稳定声明 ID、语义版本、归一化／去重、组合解析和可用能力；未知版本完整保留并明确提示，不静默丢弃“计划”等限制后执行。
2. 编辑器事务、草稿修订、撤销／重做、跨窗口同步与冲突恢复。合并正文时不能无条件合并声明导致扩大行为；无法安全合并时保留原始恢复副本供选择。
3. 提交编译、主进程校验、消息元数据、队列持久化／编辑、重新编辑和失败重试。主进程从可信已校验文档派生运行声明，不接受正文与旁路字段两套不一致结果。
4. `composerSubmissionKey()` 当前主要依赖正文树，须将规范化声明及语义版本纳入身份，避免同文不同阶段被错误去重；同一失败快照重试仍使用原身份。
5. 发送后轮换草稿的比较、`mergeComposerDocuments()` 的相同正文判断也要比较声明，不能把发送中的新选择清空或当成同一份草稿。
6. Agent 启动时的有效模式、工具筛选、派发校验、子任务继承和上下文编译。历史消息中的旧声明只解释当时任务，不自动成为后续每轮的限制。
7. 复制、导出与历史展示有明确降级文本，例如“任务声明：自动化、计划”；纯文本粘贴仅恢复文本，不因标签字样授予工具或自动切换阶段。

细节字段名随实施定稿。计划阶段工具边界未完成前，不上线一个只改变提示词的“计划”可用标签。

## 7. 实施顺序与验收

1. 先落实两个声明的共享契约、默认值、组合含义与会话模式解析，完成阶段执行约束。
2. 接入草稿／发送／队列／恢复，覆盖旧文档迁移和幂等身份，再接附加菜单和消息标签。
3. 联调运行状态与光标有效位置处理，验证直接导航与必要交互均能正常完成任务。
4. 运行针对性逻辑和真实应用检查，记录实际能力与剩余边界；首批不顺带开发调研／验证及任意自定义声明。

验收重点：自动化可零鼠标输入完成任务；需要点击时真实输入及光标正确；计划与组合声明不实施目标改动，但必要读取和计划产物可用；快速问答的单条覆盖不更改长期配置；声明独立于权限和批注；声明变更、撤销、发送期间新编辑、队列、重试、未知版本和跨窗口冲突不丢失；无任务正文时不误发；附加仍为 HTML 且不新增网页截图替换。

本轮已实现正式声明项及其消息链路。没有重跑安装版用户的真实自动化任务；声明验收使用隔离资料与本地模型固定响应，打包状态以主任务的整合结果为准。

## 8. .6 核对后补齐的消息与运行契约

### 8.1 统一语义身份和队列收据

当前实现由 `composerSemanticIdentity()` 生成统一语义身份，`composerSubmissionKey()` 与 `electron/modules/agent-inbox.ts` 的 fingerprint 共用该契约，纳入声明 ID、语义版本和实际内容；前端提交、主进程收据、失败恢复使用同一规则。同文不同阶段是不同提交，同一冻结快照重试保持原身份。

队列编辑通过预期修订更新尚未执行的项及其内容指纹，不将编辑变成重复入队；原提交的重试仍只得到原接受结果，不用旧重试覆盖新编辑。编辑后的执行快照按当前队列修订冻结，开始执行后不允许原客户端继续修改该快照。字段名和收据格式随共享契约定稿，不能让前后端分别实现不一致哈希。

### 8.2 不可发送与不可丢弃是两种状态

仅含声明的草稿仍不可发送，但它有用户状态，必须保存、同步、恢复和撤销；不能继续以 composerDocumentEmpty() 的正文结果判断可以清空。草稿状态存在性与发送有效性分开校验。

旧纯文本队列编辑会用 composerDocumentFromLegacy() 重建文档；未显式修改声明时保留原声明及限制，只有用户明确删除才移除。正文相同但声明不同的跨窗草稿不能按“相同内容”合并或取并集，应保留冲突副本。未知 schema／语义版本完整保留，不能降级成无计划限制的普通消息再执行。

### 8.3 共同的运行约束快照

Agent 启动保存本轮阶段、声明语义版本、来源消息／队列修订及子任务继承范围，权限仍按当时有效策略复核。原始调用 main.ts 的开始／重试、runtime 的确认后 resume（可能 userText 为空）、中断恢复、重新执行、子对话启动和后续跟进，全部从该快照恢复，不靠重新扫描正文猜阶段。

计划经权限确认或恢复后仍是计划；批准某个只读能力不把阶段变为执行。子任务默认继承本轮限制，明确新用户指令改变阶段时按该次授权建立新快照，不能让旧 finally／回包更改新任务。

带声明消息在运行中只入队的首批规则由主进程 AgentInbox 和 runtime 同时执行；不能只把编辑器按钮改成“入队”，仍允许远程接口／队列“立即插入”旁路改变当前任务。普通不改阶段的补充沿原有规则；已派发动作不被追溯重解释。

### 8.4 新增验收

覆盖两端同文不同声明的去重、队列编辑后旧重试、纯声明草稿的重启／撤销、兼容文本编辑、未知版本、授权暂停后空正文 resume、崩溃恢复、计划子任务及接口直接插入。先验证计划的派发约束和快照，再上线声明标签；`.6` UI 验证不能代替这一组检查。


## 9. 本轮实现与验收记录

- `shared/task-declarations.ts` 统一声明注册、别名、规范化及阶段派生。自动化与计划同时选中仍为 `plan`；声明不切换长期回答方式、权限或浏览器控制权。
- `ComposerDocument` schema 3 保存单条声明，旧 schema 1／2 迁移到 3。未知声明版本或 ID 可完整保存在草稿、队列编辑副本和恢复记录中，正文预览与保存使用 `previewComposerDocument()`；可执行提交、重试身份与队列派发使用严格 `compileComposerDocument()`，不识别的语义会阻断发送。兼容模式的纯文本草稿／队列编辑保留原声明，只有显式结构化编辑才可移除。
- 无正文且无资料时仍不能发送，但纯声明属于有内容的草稿状态；保存、比较、跨窗口 CAS、恢复去重和已接受回包都纳入声明。无声明文档保留旧收据身份；正文相同而声明不同不合并，冲突副本保留。输入区会在成功接收后开始新的无声明草稿，旧回包不能清除新草稿已选声明。
