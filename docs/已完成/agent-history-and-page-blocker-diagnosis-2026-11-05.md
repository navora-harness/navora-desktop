## 1. 已发生的操作被后续回答错误否定

自动化测试原轮保存了 19 次真实工具调用：有点击派发回执、三次文本输入确认、Tab 派发，以及页面脚本对字段和焦点的回读。宿主结束摘要为：派发动作 11、确认字段 3、计入的观察 5、Tab 派发 1。事件派发、字段确认和任务完整完成仍须区分；这组证据足以否定“此前完全没有调用工具或执行任何操作”。

原轮确有两个工具失败：

- `browser_query_deep` 返回 `browser_operation_invalidated`，要求等待恢复并重新观察。该回执没有细分控制权、布局、取消或文档变化等具体失效来源，不能仅凭它认定是用户手动接管。
- `browser_hover` 使用了旧 ref，返回 `stale_element_ref`。其间已有新的页面观察，不能继续假设最初 ref 仍然有效。页面没有下拉框也已由查询和 DOM 统计确认，最初选择的测试页无法覆盖全部操作。

随后用户追问失败原因。该条用户消息的 `modelIdentity.executionMode` 为 `auto`、声明列表为空。新的运行只有 1 轮模型请求、0 次工具调用，其宿主摘要各项为零。Agent 随后把这些零值解释成此前从未操作，并称真实的失效错误也是编造的；这段解释与保存的回执相矛盾。

### 代码原因

1. [execution-mode.ts](../../shared/execution-mode.ts) 的 `needsAgentTools()` 只判断当前句子。该追问未命中外部操作词，却命中“为什么”，因此走快速问答。
2. [agent-runtime.ts](../../electron/modules/agent-runtime.ts) 的快速问答分支只保留 user／assistant 文本；工具回执、结束摘要和元数据均未带回。完整 Agent 分支的历史构造也跳过 tool 消息，只保留其他角色的文本，因此仅强制 Agent 模式不能完整修复。
3. 每次运行新建 `AgentProgressPolicy`，请求中却统一注入未标明 run／turn 作用域的“宿主执行事实”。新轮的零计数容易被误读成整段对话的执行统计。
4. [agent-progress-policy.ts](../../shared/agent-progress-policy.ts) 的观察计数不包含 `browser_evaluate`；键盘独立效果标志也未根据这些回读更新。统计为零或未确认，不能反向否定现存回执。

### 修复要求

- 执行摘要明确标识当前 `runId`、`turnId` 和统计范围，说明“当前轮零次”不能否认历史操作。
- 两条回答路径都接收宿主生成的历史执行摘要：按任务轮聚合已执行、已确认、失败、未核实及停止原因，并可定位必要回执。保留隐私、长度预算和网页内容不受信的边界，不把原始工具正文升级为系统指令。
- 识别“刚才为什么失败／之前执行了吗”等与前序任务相关的追问。解释不一定需要新工具，但必须保留已存在的执行证据；不得让回答模式变化变成“此前从无工具权限”的证明。
- 历史以完整任务轮取舍，保底保留最近相关任务的宿主摘要；不能只截最近若干条消息后留下助手自述。
- 将可观察的键盘／字段回读与计数口径分开说明。不能把任意 `browser_evaluate` 成功一律算作业务确认，也不能忽略明确回读证据。
- 为失效错误补充脱敏的原因类别、文档／控制代次及发生阶段，避免后续诊断把所有失效解释成同一种情况。

验收覆盖：真实工具成功后追问、部分失败后解释、auto／chat／agent 切换、重启和长历史；验证新轮零计数不会覆盖前轮证据，旧 ref 不会无观察重放。

### “本条：自动化”的发送语义

这是随单条消息提交的任务声明。发送被宿主成功接收后，从输入框清除并保留在已发送消息的元数据与展示中；失败保留草稿，旧回执不能清除下一份新草稿的声明。后续消息不自动继承，底部 auto／chat／agent 模式独立持续。`ChatStore.clearDraftRevision()`、`useComposerDraft.acknowledge()` 和现有任务声明界面夹具已有对应逻辑。本次未更改这项语义；不应为掩盖历史证据问题而把一次性声明偷偷改成持续模式。

## 2. 网站已出现验证，Agent 仍读取底层商品内容

用户截图显示人机验证页面。商品整理段的两次 `browser_get(agent_find)` 保存结果已经包含验证服务的跨域 frame，但其覆盖状态为 `skipped`、原因为 `MAX_NODES`，整体快照 `complete:false`、`truncated:true`。这些是需要补查的线索；仅有验证域名不能证明该 frame 当时可见并阻断，也无法仅据截图与历史确定同一个 windowId 及精确出现时刻。

随后 `browser_evaluate` 仍可读取底层商品 DOM，进一步获得商品图片地址，下载和文件写入也保存了成功回执。这些数据结果并不证明前台页面没有验证遮挡；同样，出现验证也不能据此把已经提取的数据全部判为虚构。

另有一次提取脚本因对空值调用 `.slice()` 失败，下一次脚本已加空值保护并成功。这是独立的脚本错误，不是“无浏览器工具”的证据。

### 代码原因

- [browser-tools.ts](../../electron/modules/browser-tools.ts) 的原生观察分支默认 `maxNodes=300`，仅返回快照和 refs，没有独立的验证码／前台阻断摘要。顶层 `partial` 目前来自等待／加载状态，与原生快照覆盖不完整分开；`ok:true` 不代表观察了全部 frame。
- `browser_evaluate` 成功执行与序列化即返回 `ok:true`。脚本能够读取 DOM，不等于用户能看到或操作相应内容。
- 当前公开原生元素提供可见性、边界等字段，没有统一的前台遮挡／阻断结论。不能将 `visible:true` 当作无遮挡且可交互。
- [page-digest.ts](../../shared/page-digest.ts) 按正文预算选取元素，其他 frame 使用剩余预算；极限回退还可能省去 frame 清单。验证线索没有独立的保底通道。
- 这是现有传递路径的风险，尚不能据此断言本次验证 frame 确实被模型请求裁掉；聊天日志正文的显示截断也不等于发给模型的截断。
- [agent-prompt.ts](../../shared/agent-prompt.ts) 已要求需要登录或站点验证时说明状态并保留会话；目前缺少稳定的宿主识别与状态传递，单纯再加一句提示词不足以解决。

### 修复要求

1. 提供独立、短小且带页面／文档身份和观测时间的阻断摘要。建议区分 `none / suspected / confirmed / unknown`，附类型、有限证据、是否需要用户操作；这是拟议的应用协议，不是当前内核已提供的接口。
2. 阻断识别独立于业务选择器和正文节点预算，结合 frame 清单、可见性、遮挡、验证提示等信号。验证域名仅作为疑似证据，避免误判隐藏 frame 或后台同步组件。
3. 可疑 frame 被节点预算跳过时，明确“尚未排除验证阻断”，允许一次有针对性的只读补查；需要视觉核实时使用观察用途截图，不作为替代 View 的图片。
4. 模型压缩与历史恢复保底保留该摘要，区分脚本执行成功、数据读到、页面受阻和用户目标完成。不得因底层 DOM 可读而默认为可继续交互。
5. 确认需要本人验证后，暂停该页面后续自动操作，告知用户并保留会话，通过现有人工接管流程等待用户完成。恢复后重新观察页面，不盲目重放旧输入、提交或下载。识别和交还验证不包含自动解题或绕过站点验证。
6. 避免永久缓存阻断：按页面／文档代次失效并重新核实。未知状态如实报告，不能将检测失败当作没有阻断。

验收覆盖：跨域验证 frame 被预算跳过、底层 DOM 仍可读、隐藏验证 frame、普通 cookie／对话框遮罩、页面导航、用户完成验证后恢复，以及摘要截断。使用隔离合成夹具，不重放真实用户验证或依赖第三方站点稳定性。
